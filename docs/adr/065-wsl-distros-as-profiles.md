# ADR 065 — WSL distributions are profiles the machine supplies

- Status: Accepted
- Date: 2026-11-24
- Related: `crates/winui/src/wsl.rs`, `crates/winui/src/app.rs`,
  ADR 023, ADR 034

## Context

Windows Terminal offers a profile per installed WSL distribution, generated by
`WslDistroGenerator.cpp` at startup. A Windows user who runs Ubuntu through WSL
expects it in the drop-down next to the shells, not behind a profile they have
to hand-write and keep current.

The list is not a setting. It is a fact about the machine: distributions are
installed, renamed and unregistered outside the terminal, and a copy written to
`settings.toml` would be stale from the moment it was saved.

## Decision

- `winui::wsl` runs `wsl.exe -l -q` once at startup and once per settings
  reload, and turns each name into a profile: `command = "wsl.exe"`,
  `args = ["-d", <distro>]`, `title = <distro>`.
- The profiles are merged **after** the file's, in the list the shell offers;
  they are not added to `settings::Settings`. The settings dialog and the writer
  keep working from the parsed file, so a save re-writes exactly the profiles
  the user wrote and the distro list survives untouched.
- A distribution whose name matches a profile in the file is dropped from the
  merge. The file wins: it is what the user wrote, and two menu rows with one
  name would resolve to whichever was found first.
- The query is run with `CREATE_NO_WINDOW`. Without the flag `wsl.exe` flashes a
  console window on a machine whose default is not the new terminal host.
- The output's encoding is decided by its bytes, not by the WSL version. The
  query writes UTF-16LE when redirected and UTF-8 when the console code page is
  already UTF-8, and which one it picks has changed between releases; a stream
  of ASCII names with a zero in every second byte is UTF-16LE.
- A machine with no WSL, or a query that fails, offers no distro profiles. It is
  not an error: the shells the file names still work.

## Rationale

Keeping the generated profiles out of `Settings` is the decision that makes the
rest simple. The settings window, the preview and the writer all read one value,
so there is no "was this profile generated?" flag to carry through the draft,
and no way for a save to bake one machine's distro list into another machine's
file.

Merging at the shell rather than in `settings` also keeps `settings` free of
`cfg(windows)` and of process spawning, which is the layering the port relies on
(ADR 001).

## Consequences

- The menu's order is the file's profiles, then the distros in the order
  `wsl.exe` lists them, then `Settings` and `About`.
- `default_profile` cannot name a distribution: only the file's profiles are in
  `Settings`, and a name that matches nothing is not replaced by another profile
  (ADR 023). A distro is started from the drop-down.
- Startup gains one process spawn. It is on the UI thread, before the window
  shows, and is bounded by `wsl.exe` answering the query.
- `TerminalSettings::for_profile` is given the generated profile directly, so a
  distro tab is titled after the distro rather than `wsl`.
- A distribution that is registered while the terminal runs appears on the next
  settings reload (the same one-second poll, ADR 025), not immediately.

## Alternatives considered

- **Writing the distro profiles into the settings file.** They would be stale,
  they would be copied to another machine, and a user who unregistered a distro
  would keep a dead menu row until they edited the file by hand.
- **A hand-written profile per distro in the default file.** The default file
  cannot know what is installed, and a wrong guess is a menu row that fails to
  start.
- **Reading the registry (`HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss`).**
  It is a second, undocumented source of the same list, and WSL's own command is
  the one upstream uses.
- **Querying on a worker thread and updating the menu when it answers.** The
  spawn is short and happens once per reload; a background thread would need a
  message, a lock and a case where the menu opens before the answer.
